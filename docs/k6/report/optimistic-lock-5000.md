# Optimistic Lock 부하 테스트 보고서 (5000명)

## 개요

- 대상 기능: 같은 행성에 대한 동시 참여 요청
- 시나리오: 일반 로그인으로 5000명 회원 생성 후, 동일 행성에 대해 5000명이 동시에 참여 요청
- 목적: 대규모 동시성 상황에서 낙관적 락 적용 시 처리량, 충돌 비율, 응답 시간 특성을 확인

## 테스트 조건

- 도구: `k6`
- 스크립트: [`planet-join-load-test.js`](/Users/simjonghan/source_code/planetrush-api/docs/k6/planet-join-load-test.js)
- 사용자 수: `5000`
- 사전 준비: 일반 로그인 5000건 성공
- 본 요청: `POST /api/v1/planets/{planet-id}` 동시 5000건
- 잠금 방식: 낙관적 락 시나리오

## 실행 결과 요약

### 로그인 단계

- 로그인 성공률: `100%` (`5000 / 5000`)
- 평균 로그인 응답 시간: `14.08ms`
- p95 로그인 응답 시간: `17.70ms`

해석:

- 회원 생성 및 토큰 발급 구간은 5000명 규모에서도 안정적으로 처리되었다.
- 병목은 로그인 단계가 아니라 행성 참여 단계에 집중된다.

### 행성 참여 단계

- 전체 참여 요청 수: `5000`
- 성공 응답 비율 `200`: `0.20%` (`10 / 5000`)
- `400` 응답 비율: `0.00%` (`0 / 5000`)
- 기타 응답 비율: `99.80%` (`4990 / 5000`)
- 실패 카운트: `4990`

응답 시간:

- 평균: `1510.97ms`
- 중앙값: `1588.82ms`
- p90: `2094.36ms`
- p95: `2115.05ms`
- 최대: `5541.00ms`

HTTP 기준:

- 전체 요청 수: `10000`
- 전체 HTTP 실패율: `49.90%` (`4990 / 10000`)

주의:

- 전체 HTTP 요청 10000건은 로그인 5000건 + 행성 참여 5000건의 합이다.
- 실패 4990건은 사실상 행성 참여 단계에서 발생한 실패로 해석할 수 있다.

## 관찰 사항

1. 로그인 단계는 5000명 규모에서도 모두 성공했다.
2. 행성 참여 요청 5000건 중 실제 성공은 10건뿐이었다.
3. 실패 응답 대부분이 `400`이 아니라 `other`로 집계되었다.
4. `join request completed` 체크가 98%인 것은 일부 요청이 응답 자체를 정상적으로 받지 못했음을 의미한다.
5. 행성 참여 응답 시간은 평균 약 1.5초, p95 약 2.1초 수준이었다.
6. 성공률은 이전 기록보다 더 낮아졌고, 사실상 대부분의 요청이 비정상 실패로 귀결되었다.

## 200명 낙관적 락 결과와 비교

| 항목 | 200명 | 5000명 |
|---|---:|---:|
| 로그인 성공률 | 100% | 100% |
| 행성 참여 성공률(200) | 5.00% | 0.20% |
| 행성 참여 실패율(other) | 95.00% | 99.80% |
| 평균 참여 응답 시간 | 281.65ms | 1510.97ms |
| 중앙값 참여 응답 시간 | 290.77ms | 1588.82ms |
| p95 참여 응답 시간 | 343.70ms | 2115.05ms |
| 최대 참여 응답 시간 | 359.85ms | 5541.00ms |
| 실패 건수 | 190 | 4990 |

해석:

- 5000명 규모에서는 성공률이 급격히 악화되었다.
- 응답 시간은 200명 테스트보다 크게 늘었고, 대규모 충돌 상황에서 낙관적 락의 비용이 분명하게 드러났다.
- 특히 실패 대부분이 `other` 응답이라는 점에서, 충돌 제어보다 예외 처리 부재가 더 심각한 운영 문제로 보인다.

## 해석

이번 결과는 "낙관적 락이 빠르다"는 일반론이 고충돌 상황에서는 그대로 성립하지 않음을 보여준다.

특히 다음 해석이 가능하다.

1. 같은 자원에 대한 동시 충돌이 매우 많아지면서 성공 요청이 거의 사라졌다.
2. 충돌 예외가 비즈니스 오류 코드로 정리되지 않아 대부분 `other` 응답으로 떨어지고 있다.
3. 일부 요청은 응답 자체가 정상적으로 완료되지 못해 `join request completed` 체크 실패로 나타났다.
4. 대규모 경쟁 상황에서는 낙관적 락도 충분히 긴 지연 시간을 만든다.

즉 현재 구현에서는 낙관적 락이 "짧게 실패하는 빠른 전략"으로 동작하지 않고, "상당수 요청이 실패하고 일부는 응답 완료조차 불안정한 전략"에 가깝다.

## 결론

- 로그인 준비 단계는 매우 안정적이다.
- 하지만 동일 행성에 대한 5000건 동시 참여 요청에서는 낙관적 락만으로 안정적인 처리 품질을 확보하지 못했다.
- 성공률 `0.20%`는 사실상 실패에 가깝다.
- 실패 건수 `4990건`과 `other 99.80%`는 충돌 처리 정책이 API 수준에서 정리되지 않았음을 보여준다.
- p95 응답 시간 `2.12초`도 동시 가입 API로는 충분히 긴 수준이다.
- 현재 병목은 단순한 락 선택 문제가 아니라, 충돌 대응 정책, 예외 처리, 재시도 전략, API 응답 설계 전반에 있다.

## 권장 후속 조치

1. `ObjectOptimisticLockingFailureException` 또는 `OptimisticLockException` 전용 핸들러를 추가해야 한다.
2. 실패 응답 body와 status를 수집해 실제 실패 유형을 분류해야 한다.
3. 충돌 시 즉시 실패할지, 짧은 재시도를 둘지 정책을 명확히 해야 한다.
4. 인기 행성/마감 임박 행성처럼 충돌이 많은 구간은 비관적 락 또는 별도 큐잉 전략도 검토해야 한다.
5. 동일 조건에서 1000명, 2000명, 5000명처럼 단계별로 재측정해 성능이 무너지는 지점을 찾는 것이 필요하다.
