# Pessimistic Lock 부하 테스트 보고서 (5000명)

## 개요

- 대상 기능: 같은 행성에 대한 동시 참여 요청
- 시나리오: 일반 로그인으로 5000명 회원 생성 후, 동일 행성에 대해 5000명이 동시에 참여 요청
- 목적: 대규모 동시성 상황에서 비관적 락 적용 시 처리량, 대기 시간, 실패 양상을 확인

## 테스트 조건

- 도구: `k6`
- 스크립트: [`planet-join-load-test.js`](/Users/simjonghan/source_code/planetrush-api/docs/k6/planet-join-load-test.js)
- 사용자 수: `5000`
- 사전 준비: 일반 로그인 5000건 성공
- 본 요청: `POST /api/v1/planets/{planet-id}` 동시 5000건
- 잠금 방식: 비관적 락 시나리오

## 실행 결과 요약

### 로그인 단계

- 로그인 성공률: `100%` (`5000 / 5000`)
- 평균 로그인 응답 시간: `12.59ms`
- p95 로그인 응답 시간: `17.53ms`

해석:

- 회원 생성 및 토큰 발급 단계는 5000명 규모에서도 안정적으로 수행되었다.
- 병목은 행성 참여 단계에 집중된다.

### 행성 참여 단계

- 전체 참여 요청 수: `5000`
- 성공 응답 비율 `200`: `0.20%` (`10 / 5000`)
- `400` 응답 비율: `0.00%` (`0 / 5000`)
- 기타 응답 비율: `99.80%` (`4990 / 5000`)
- 실패 카운트: `4990`

응답 시간:

- 평균: `2994.47ms`
- 중앙값: `2844.43ms`
- p90: `4643.00ms`
- p95: `4797.91ms`
- 최대: `6127.08ms`

HTTP 기준:

- 전체 요청 수: `10000`
- 전체 HTTP 실패율: `50.00%` (`5000 / 10000`)

주의:

- 전체 HTTP 요청 10000건은 로그인 5000건 + 행성 참여 5000건의 합이다.
- 실패 4990건은 사실상 행성 참여 단계에서 발생한 실패로 해석할 수 있다.

## 관찰 사항

1. 로그인 단계는 5000명 규모에서도 모두 성공했다.
2. 행성 참여 요청 5000건 중 실제 성공은 10건뿐이었다.
3. 실패 응답 대부분이 `400`이 아니라 `other`로 집계되었다.
4. `join request completed` 체크 실패가 146건 존재해 일부 요청은 응답 완료 자체도 불안정했다.
5. 참여 요청 응답 시간은 평균 약 3.0초, p95 약 4.8초로 매우 길다.

## 해석

이번 결과는 5000명 대규모 동시 가입 상황에서 비관적 락이 긴 대기 시간을 만들면서도, 현재 구현 수준에서는 극히 일부 요청만 성공시키는 수준임을 보여준다.

특히 다음 해석이 가능하다.

1. 동일 row에 대한 직렬화 대기가 크게 발생했다.
2. 대기 끝에 안정적인 성공으로 수렴하지 않고, 대부분 비정상 응답으로 끝났다.
3. 실패 응답이 모두 `other`인 점에서 락 경쟁 실패가 비즈니스 오류 코드로 정리되지 않았다.
4. 일부 요청은 네트워크 또는 연결 레벨에서 응답 완료가 되지 못했을 가능성도 있다.

즉 현재 구현에서는 비관적 락이 "정합성을 위해 기다리게 하는 전략"이 아니라, "오래 기다린 뒤 모두 실패하는 전략"에 가깝게 보인다.

## 결론

- 로그인 준비 단계는 안정적이다.
- 하지만 동일 행성에 대한 5000건 동시 참여 요청에서는 비관적 락만으로 처리 품질을 확보하지 못했다.
- 성공률 `0.20%`는 실질적으로 거의 실패에 가깝다.
- 실패 건수 `4990건`과 `other 99.80%`는 예외 처리 및 충돌 대응 정책이 정리되지 않았음을 보여준다.
- p95 응답 시간 `4.80초`, 최대 `6.13초`는 동시 가입 API로서 매우 긴 수준이다.

## 권장 후속 조치

1. 실패 응답 body와 status를 수집해 실제 실패 유형을 분류해야 한다.
2. 비관적 락 구간의 DB 대기 시간과 톰캣 스레드 점유 시간을 함께 관찰해야 한다.
3. 락 경쟁 실패를 명시적 응답 코드로 정리해야 한다.
4. 동일 자원에 대한 초고밀도 요청은 큐잉, 선착순 토큰화, 별도 예약 테이블 전략도 검토해야 한다.
5. 5000명 규모에서는 애플리케이션 락 전략뿐 아니라 커넥터, DB pool, 네트워크 수용량까지 함께 봐야 한다.
