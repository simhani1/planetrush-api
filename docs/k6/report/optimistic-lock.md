# Optimistic Lock 부하 테스트 보고서

## 개요

- 대상 기능: 같은 행성에 대한 동시 참여 요청
- 시나리오: 일반 로그인으로 200명 회원 생성 후, 동일 행성에 대해 200명이 동시에 참여 요청
- 목적: 낙관적 락 적용 상태에서 동시 가입 요청 처리 결과와 충돌 양상을 확인

## 테스트 조건

- 도구: `k6`
- 스크립트: [`planet-join-load-test.js`](/Users/simjonghan/source_code/planetrush-api/docs/k6/planet-join-load-test.js)
- 사용자 수: `200`
- 사전 준비: 일반 로그인 200건 성공
- 본 요청: `POST /api/v1/planets/{planet-id}` 동시 200건
- 잠금 방식: 낙관적 락 시나리오

## 실행 결과 요약

### 로그인 단계

- 로그인 성공률: `100%` (`200 / 200`)
- 평균 로그인 응답 시간: `21.45ms`
- p95 로그인 응답 시간: `26.21ms`

해석:

- 회원 생성 및 토큰 발급 단계는 안정적으로 수행되었다.
- 본 테스트 병목은 행성 동시 참여 구간에 집중된다.

### 행성 참여 단계

- 전체 참여 요청 수: `200`
- 성공 응답 비율 `200`: `5.00%` (`10 / 200`)
- `400` 응답 비율: `0.00%` (`0 / 200`)
- 기타 응답 비율: `95.00%` (`190 / 200`)
- 실패 카운트: `190`

응답 시간:

- 평균: `281.65ms`
- 중앙값: `290.77ms`
- p90: `336.82ms`
- p95: `343.70ms`
- 최대: `359.85ms`

HTTP 기준:

- 전체 요청 수: `400`
- 전체 HTTP 실패율: `47.50%` (`190 / 400`)

주의:

- 전체 HTTP 요청 400건은 로그인 200건 + 행성 참여 200건의 합이다.
- 실패 190건은 사실상 행성 참여 단계에서 발생한 실패로 볼 수 있다.

## 관찰 사항

1. 사전 로그인 200건은 모두 성공했다.
2. 동시 행성 참여 요청 200건 중 성공은 10건이었다.
3. 실패 응답 대부분이 `400`이 아니라 `other`로 집계되었다.
4. 낙관적 락 충돌 또는 동시성 관련 예외가 비즈니스 실패 응답으로 정리되지 않았을 가능성이 높다.

## 해석

낙관적 락 시나리오에서도 성공률은 매우 낮고, 실패 요청 대부분이 명시적 비즈니스 응답이 아니라 기타 응답으로 처리되었다.

이는 아래 상황을 시사한다.

- 낙관적 락 충돌이 전역 예외 핸들러 없이 5xx로 전파되고 있다.
- 중복 가입 또는 버전 충돌이 API 명세상 실패 코드로 매핑되지 않았다.
- 현재 구현은 충돌을 "예상 가능한 경쟁 실패"로 다루지 않고, 시스템 실패처럼 처리하고 있을 가능성이 높다.

즉 낙관적 락을 적용했다고 해도, 현재 상태에서는 충돌 제어의 사용자 경험이나 API 안정성까지 확보된 것은 아니다.

## 비관적 락 결과와 비교

같은 200명 동시 가입 기준으로 비교하면:

| 항목 | 비관적 락 | 낙관적 락 |
|---|---:|---:|
| 행성 참여 성공률(200) | 4.50% | 5.00% |
| 행성 참여 실패율(other) | 95.50% | 95.00% |
| 평균 참여 응답 시간 | 335.99ms | 281.65ms |
| p95 참여 응답 시간 | 486.23ms | 343.70ms |
| 최대 참여 응답 시간 | 530.22ms | 359.85ms |

해석:

- 성공률은 두 시나리오 모두 매우 낮고 큰 차이가 없다.
- 낙관적 락이 응답 시간 측면에서는 더 짧았다.
- 하지만 충돌 처리 결과가 여전히 대부분 비정상 응답으로 떨어지고 있어, 성능보다 예외 처리 보완이 더 시급하다.

## 결론

- 로그인 준비 단계는 안정적이다.
- 낙관적 락 적용 상태에서도 동시 가입 200건에 대한 안정적 처리에는 실패했다.
- 성공률 `5.0%`는 실서비스 관점에서 매우 낮다.
- 실패 응답의 대부분이 `400`이 아닌 기타 응답이라는 점에서, 현재 병목은 락 전략만의 문제가 아니라 예외 처리 및 충돌 대응 정책에도 있다.

## 권장 후속 조치

1. `ObjectOptimisticLockingFailureException` 또는 `OptimisticLockException` 전용 핸들러를 추가해야 한다.
2. 낙관적 락 충돌을 409 또는 명시적 비즈니스 실패 코드로 정리해야 한다.
3. k6 스크립트에 상태코드별 response body 수집을 추가해 실제 실패 원인을 확인해야 한다.
4. 충돌 시 재시도 정책을 둘지, 즉시 실패 정책을 둘지 비즈니스적으로 결정해야 한다.
5. 성공률이 아닌 "허용 가능한 충돌 응답 비율" 기준으로 다시 측정할 필요가 있다.
