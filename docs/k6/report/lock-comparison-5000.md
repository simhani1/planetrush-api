## 결과 해석

### 1. 성공률

두 시나리오 모두 성공률은 사실상 동일하다.

- 낙관적 락: `0.20%`
- 비관적 락: `0.20%`

해석:

- 5000명 규모의 초고밀도 충돌 상황에서는 어느 락 전략도 현재 구현 수준에서 유의미한 성공률을 만들지 못했다.
- 따라서 5000명 결과만 보면 "어느 락이 더 성공률이 높다"는 결론은 낼 수 없다.

### 2. 응답 시간

응답 시간은 낙관적 락이 비관적 락보다 더 짧았다.

- 평균: `1510.97ms vs 2994.47ms`
- 중앙값: `1588.82ms vs 2844.43ms`
- p95: `2115.05ms vs 4797.91ms`
- 최대: `5541.00ms vs 6127.08ms`

해석:

- 비관적 락은 row 직렬화 대기로 인해 지연 시간이 더 커졌다.
- 낙관적 락은 충돌 후 실패가 많더라도 평균 및 상위 백분위 응답 시간에서는 더 짧았다.
- 즉 5000명 급에서는 비관적 락이 "더 안전하다"기보다 "더 오래 기다리게 한다"는 특징이 더 강하게 나타났다.

### 3. 실패 패턴

두 시나리오 모두 실패 응답이 거의 전부 `other` 로 집계되었다.

- 낙관적 락: `99.80%`
- 비관적 락: `99.80%`

그리고 `join request completed` 실패 건수는:

- 낙관적 락: `63`
- 비관적 락: `146`

해석:

- 충돌 실패가 비즈니스 응답으로 정리되지 않고 있다.
- 일부 요청은 애플리케이션 예외 이전에 연결 또는 응답 완료 문제까지 겪고 있을 가능성이 있다.
- 비관적 락 쪽이 응답 완료 실패 건수가 더 많아, 고부하에서 연결/대기 영향이 더 크게 드러난 것으로 볼 수 있다.

## 5000명 규모에서 드러난 특징

### 낙관적 락

장점:

- 비관적 락보다 응답 시간이 짧다.
- 대기 시간이 상대적으로 덜 길다.
- 응답 완료 실패 건수가 더 적다.

단점:

- 성공률은 여전히 극단적으로 낮다.
- 충돌 예외가 비정상 응답으로 떨어진다.
- 대규모 충돌 상황에서는 "빠르게 실패"하지도 못하고 수 초 단위 지연이 발생한다.

### 비관적 락

장점:

- 이론상 정합성 제어 방향은 명확하다.
- 동일 자원 직렬화라는 의도 자체는 분명하다.

단점:

- 이번 결과에서는 성공률 개선이 전혀 없었다.
- 응답 시간이 낙관적 락보다 훨씬 길다.
- 응답 완료 실패 건수도 더 많다.
- 고부하에서 대기 시간이 커지면서 사용자 체감이 더 나빠질 가능성이 높다.

## 왜 이런 결과가 나왔는가

현재 결과는 락 전략 자체의 우열보다, 현재 구현의 한계를 더 강하게 보여준다.

주요 원인 후보:

1. 락 충돌 예외가 전용 핸들러 없이 5xx 또는 기타 응답으로 전파되고 있다.
2. 동시 가입 실패가 비즈니스 실패 코드로 정리되지 않았다.
3. 5000명 규모에서는 애플리케이션 로직뿐 아니라 톰캣, DB pool, 네트워크 연결 수용 한계가 함께 영향을 준다.
4. 일부 실패는 애플리케이션 내부 예외 이전에 연결/응답 레벨에서 발생했을 가능성이 있다.

즉 현재 단계에서는 "낙관적 락이 더 낫다" 또는 "비관적 락이 더 안전하다"보다, "둘 다 실패를 제대로 다루지 못한다"가 더 중요한 결론이다.

## 결론

5000명 기준 결과만 놓고 보면:

1. 성공률은 낙관적 락과 비관적 락이 사실상 동일하다.
2. 응답 시간은 낙관적 락이 더 좋다.
3. 실패 패턴은 두 전략 모두 매우 나쁘다.
4. 비관적 락은 더 오래 기다리게 하지만 성공률을 높이지 못했다.
5. 낙관적 락은 더 빠르지만 충돌 처리 정책이 없어서 대부분 실패로 끝난다.

따라서 현재 코드 기준으로는 5000명 초고부하 상황에서 낙관적 락이 상대적으로 더 나은 선택처럼 보일 수는 있다. 하지만 그 이유는 "성공률이 좋아서"가 아니라 "같이 실패해도 덜 느리기 때문"에 가깝다.

## 권장 방향

1. `ObjectOptimisticLockingFailureException`, `OptimisticLockException`, 동시성 관련 사용자 정의 예외를 명시적 응답 코드로 정리해야 한다.
2. k6 스크립트에 상태코드별 body 집계를 추가해 `other` 응답의 실제 원인을 확인해야 한다.
3. 5000명 같은 초고밀도 경쟁 구간은 락 전략 외에 큐잉, 선착순 토큰화, 예약 테이블 분리 같은 구조적 대안도 검토해야 한다.
4. 실서비스 관점에서는 "성공률"과 함께 "응답 완료율", "정합성 보장", "사용자 체감 지연"을 함께 기준으로 봐야 한다.
5. 현재 상태에서 락 전략을 선택해야 한다면, 낙관적 락 + 충돌 핸들링 + 재시도/즉시실패 정책 정비가 비관적 락보다 더 현실적일 가능성이 높다.
