# Pessimistic Lock 부하 테스트 보고서

## 개요

- 대상 기능: 같은 행성에 대한 동시 참여 요청
- 시나리오: 일반 로그인으로 200명 회원 생성 후, 동일 행성에 대해 200명이 동시에 참여 요청
- 목적: 비관적 잠금 적용 상태에서 동시 가입 요청 처리 결과와 병목 지점을 확인

## 테스트 조건

- 도구: `k6`
- 스크립트: [`planet-join-load-test.js`](/Users/simjonghan/source_code/planetrush-api/docs/k6/planet-join-load-test.js)
- 사용자 수: `200`
- 사전 준비: 일반 로그인 200건 성공
- 본 요청: `POST /api/v1/planets/{planet-id}` 동시 200건
- 잠금 방식: 비관적 잠금 시나리오

## 실행 결과 요약

### 로그인 단계

- 로그인 성공률: `100%` (`200 / 200`)
- 평균 로그인 응답 시간: `18.41ms`
- p95 로그인 응답 시간: `22.73ms`

해석:

- 회원 생성 및 JWT 발급 단계는 병목이 크지 않았다.
- 본 테스트의 주요 병목은 로그인 단계가 아니라 행성 참여 단계에 있다.

### 행성 참여 단계

- 전체 참여 요청 수: `200`
- 성공 응답 비율 `200`: `4.50%` (`9 / 200`)
- `400` 응답 비율: `0.00%` (`0 / 200`)
- 기타 응답 비율: `95.50%` (`191 / 200`)
- 실패 카운트: `191`

응답 시간:

- 평균: `335.99ms`
- 중앙값: `345.44ms`
- p90: `460.39ms`
- p95: `486.23ms`
- 최대: `530.22ms`

HTTP 기준:

- 전체 요청 수: `400`
- 전체 HTTP 실패율: `47.75%` (`191 / 400`)

주의:

- 전체 `400`건은 로그인 200건 + 행성 참여 200건을 합친 값이다.
- 실패 `191`건은 사실상 행성 참여 단계에서 발생한 것으로 해석할 수 있다.

## 관찰 사항

1. 사전 로그인 200건은 모두 성공했다.
2. 동시 행성 참여 요청 200건 중 실제 성공은 9건뿐이었다.
3. 실패 응답이 `400`이 아니라 `other`로 집계되었다.
4. 즉 현재 실패는 도메인 검증에 따른 정상 거절보다, 처리되지 않은 예외나 5xx 계열 응답일 가능성이 높다.

## 해석

현재 결과는 비관적 잠금 자체의 지연보다는, 동시 가입 충돌 시 예외 처리가 충분히 정리되지 않았음을 보여준다.

특히 아래 가능성이 높다.

- 중복 가입 요청 예외가 전용 핸들러 없이 전파됨
- 잠금 경합 중 발생한 예외가 4xx가 아니라 5xx로 응답됨
- 최대 참여 인원, 중복 거주자, 잠금 재시도 실패 등이 비정상 응답으로 처리됨

즉 "락이 걸려 순차적으로 안정 처리된다"기보다는, "락 경합 상황에서 상당수 요청이 비정상 실패한다"는 결과에 가깝다.

## 결론

- 로그인 준비 단계는 안정적이다.
- 같은 행성에 대한 동시 가입 200건 처리에서는 안정성이 낮다.
- 성공률 `4.5%`는 실서비스 기준으로 매우 낮다.
- 실패 요청 대부분이 `400`이 아닌 기타 응답으로 떨어진 점은 예외 처리 미비 신호다.

## 권장 후속 조치

1. 행성 참여 실패 응답의 실제 HTTP status와 body를 로그로 수집해야 한다.
2. `DuplicatedRegisterResidentRequestException` 같은 동시성 관련 예외에 대한 전용 핸들러를 추가해야 한다.
3. 정상적인 경쟁 실패는 4xx 또는 명확한 비즈니스 에러 코드로 반환되도록 정리해야 한다.
4. k6 스크립트에 상태코드별 body 집계를 추가해 어떤 예외가 주로 발생하는지 확인하는 것이 좋다.
5. 성공/실패 기준을 "락 획득 성공"이 아니라 "비즈니스적으로 허용 가능한 결과"로 나눠 재측정할 필요가 있다.
